# Windows backend proposal

This document defines the proposed scope for adding Windows support to
omdrop-owl. It is intentionally separate from the Linux implementation and
does not change the behavior or packaging of the existing backend.

## Goal

Provide a Windows radio backend that implements the contract in
[`radio-backend.md`](radio-backend.md), using an external Wi-Fi radio
connected over USB. The first target is an ESP32-S3 that can receive and
inject the 802.11 frames required by OWL.

The first usable milestone is:

```text
Windows + ESP32-S3 + OWL + iPhone
```

with one successful AirDrop transfer in each direction.

## Why an external radio is required

The Linux backend relies on monitor mode and frame injection from mac80211
drivers. Windows does not provide a portable equivalent through its normal
Wi-Fi driver interface. The Windows backend therefore owns a different
radio-transport implementation rather than trying to reproduce Linux commands
such as `iw`, `ip`, or `nmcli`.

The host-side backend and the external radio communicate through the versioned
protocol in [`../windows/protocol/README.md`](../windows/protocol/README.md).

## Compatibility boundary

The following behavior remains Linux-specific and must not be changed to
accommodate Windows:

- `userspace/omdrop-discoverable`;
- NetworkManager configuration;
- polkit policy;
- AUR and Debian packaging;
- Linux Wi-Fi profiles;
- monitor and IBSS interface setup.

The Windows implementation will live under `windows/` and use Windows-native
build, process, privilege, and device APIs. Shared code is limited to
platform-neutral protocols and data formats.

## Included in the first contribution

- the radio-backend contract and Windows-specific usage documentation;
- a versioned host/radio protocol;
- a Windows serial transport;
- a fake radio for tests without hardware;
- an OWL adapter for the external radio;
- reference ESP32-S3 firmware;
- a Windows backend CLI implementing `start`, `stop`, `status`, `peers`, and
  `probe`;
- automated tests that do not require an ESP32 or an Apple device;
- a documented hardware test procedure.

## Explicitly deferred

These items are not required for the first backend contribution:

- support for the internal Windows Wi-Fi adapter;
- ESP32-C5 or 5 GHz channel support;
- a tray application;
- Explorer integration;
- an MSI installer;
- automatic updates;
- Contacts Only support;
- a graphical settings application;
- production guarantees for all Windows versions and Wi-Fi hardware.

They may be added after the backend and protocol are stable.

## Acceptance criteria

The contribution is ready for review when all of the following are true:

1. Linux builds and tests pass without requiring Windows tooling.
2. Windows protocol and transport tests run without physical hardware.
3. Invalid magic, version, length, CRC, and sequence conditions are rejected.
4. The fake radio exercises handshake, TX, RX, timeout, and disconnect paths.
5. OWL builds on a supported Windows toolchain against pinned source commits.
6. The Windows CLI implements the documented command and exit-code contract.
7. A reference ESP32-S3 can complete the protocol handshake and exchange
   frames with the host.
8. An iPhone can discover the Windows host and transfer a file in both
   directions.
9. Hardware, firmware, channel, performance, and known limitations are
   documented.

The virtual radio pipeline is considered complete before hardware work when
the OWL runtime test covers both directions: a frame generated by OWL reaches
the fake radio and returns a TX result, while a real OWL-generated radiotap
frame injected by the fake radio is accepted by the receiving OWL state. This
test is intentionally separate from AirDrop and virtual Ethernet validation.

The Windows Ethernet boundary follows the same rule: its in-memory backend is
used for deterministic tests, while a future Wintun backend will implement the
same read/write contract. The memory backend is not presented as a real
Windows network adapter and does not require driver installation.

The reference firmware builds for `esp32s3` with ESP-IDF 5.3.1 and boots in
Espressif's QEMU. A QEMU UART test has completed the OWLR `HELLO` /
`CAPABILITIES` exchange. QEMU does not emulate the Wi-Fi radio path, so this
validates firmware startup and protocol handling only; raw 802.11 RX/TX and
iPhone interoperability still require a physical ESP32-S3.

The current CLI lifecycle performs a radio handshake before reporting
`visible=true`. Simulation uses the fake radio; hardware uses the configured
COM port. On Windows, a resident worker now owns the radio handle and pumps
the session until `stop` or expiry. This validates the process/lifecycle
boundary, but it does not yet claim full discoverability or AirDrop support:
the OWL runtime and a real Windows Ethernet adapter still need to be attached
to the worker.

## Review units

The implementation should remain reviewable as these logical commits:

1. Contract and scope documentation.
2. Platform-neutral radio protocol.
3. Windows transport and fake-radio tests.
4. OWL Windows adapter.
5. ESP32-S3 reference firmware.
6. Windows backend CLI.
7. CI and hardware validation documentation.

The Linux backend should remain the default path throughout development.
